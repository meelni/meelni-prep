# SAV-388: Detect stalled feedback after dispatch

## Intent

- User request: Investigate and materially improve the reliability and performance of the complete interview-to-feedback lifecycle.
- Product/user outcome: Operators detect a feedback job that is stuck after an interview ends before a candidate waits indefinitely on the saving state.
- Why now: Production can report healthy while durable feedback work has been sent but not claimed, or generation has exceeded its lease.

## Slice

- Primary slice: Feedback/evaluation reliability.
- Secondary slices: Interview lifecycle operations and readiness.
- Relevant skill(s): `meelni-feedback-evaluation`, `meelni-livekit-interview-runtime`, `meelni-ops-connections`, `meelni-linear-workstream`.

## Linear Tracking

- Project: Meelni.
- Parent slice issue: SAV-365.
- Child deliverable issue: SAV-388.
- Current Linear state: In Progress.

## Scope

- In scope: Make service health reuse the canonical feedback queue and generation leases; detect sent-unclaimed and expired-processing work; preserve fixed public codes and bounded database evidence; add tests and docs.
- Out of scope: Provider calls from health, alert provisioning, feedback rubric changes, Production mutations, and the owner-authorized staging rehearsal.
- Assumptions: A pending sent event must be claimed within the 90-second lifecycle upper bound; generation must finish or become recoverable within its five-minute lease.

## Product Lens

- Audience: Candidates finishing an authenticated PM interview and operators responsible for recovery.
- Activation/retention/monetization/growth lever: Trust and retention through reliable completion and actionable recovery.
- Product Compass note: Feedback reliability is part of the core product promise; a false-green readiness signal is not acceptable evidence.

## Technical Plan

- Likely app files: None; the existing `/api/health` route keeps the version 1 response shape.
- Likely package/workflow files: `lib/operations/service-health.ts`, `lib/operations/service-health-store.ts`, and associated tests.
- Data or provider dependencies: Existing feedback table only; no external provider request.
- Docs/decisions to update: Service-health contract and runbook; architecture verification evidence if behavior changes materially.

## Validation

- Required commands: Targeted service-health tests, `npm run test:operations`, typecheck, and `git diff --check`.
- Optional/manual checks: Verify the rendered SQL contains explicit status predicates and lease cutoffs without identifiers.
- Fixtures or regression tests needed: Sent-unclaimed inside/outside the queue lease and processing inside/outside the generation lease.

## Rollout

- Risk level: Medium; the health endpoint may correctly become degraded where it previously returned a false healthy result.
- Backward compatibility: Response schema and fixed codes remain version 1 compatible.
- Metrics/events to watch: `feedback_dispatch_stale`, generation retry/recovery outcomes, and end-to-feedback upper-bound breaches.
- Follow-up slice: SAV-387 isolated authenticated staging rehearsal and provider-backed event verification.
