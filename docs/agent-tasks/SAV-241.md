# SAV-241 Agent Task Intake

## Intent

- User request: serialize the open migration stacks and prevent sibling or standalone PRs from reusing a Drizzle migration sequence.
- Product/user outcome: the relaunch reaches Preview and Production with one monotonic, reproducible database history.
- Why now: several independently green open PRs add migrations with the same sequence numbers.

## Slice

- Primary slice: database integration and trusted CI.
- Secondary slices: engineering operations and PR review workflow.
- Relevant skills: codebase architecture, Linear workstream, engineering memory, PR prep.

## Linear Tracking

- Project: Meelni.
- Parent slice issue: SAV-171.
- Child deliverable issue: SAV-241.
- Current Linear state: In Progress.

## Scope

- In scope: pure Drizzle-path ownership parsing, cross-PR collision detection, paginated GitHub PR/file inventory, exact-head Check Runs, event and scheduled revalidation, regression tests, and operations documentation.
- Out of scope: renumbering the existing open migrations, merging migration stacks, remote database operations, and changing the relaunch flag.
- Assumptions: every non-removed change to a direct `lib/db/migrations/<numeric>_*.sql` file claims that sequence. Removed and renamed-away migration history fails closed as an immutable-history violation. GitHub metadata and file lists are untrusted external input. The verifier and workflow always come from the default branch.

## Product Lens

- Audience: engineers, reviewers, and coding agents preparing the relaunch.
- Lever: launch reliability and data safety.
- Product Compass note: this is an operational merge guardrail, not a customer-facing product change.

## Technical Plan

- Likely app files: none.
- Likely workflow files: the trusted relaunch integration workflow, pure Node modules, GitHub adapters, and offline tests.
- Data or provider dependencies: read-only GitHub pull-request/file APIs and exact-head Check Runs; no database connection.
- Docs/decisions to update: stacked-PR, tooling, and database-migration runbooks. No new architecture decision is needed because this enforces the accepted forward-only migration contract.

## Validation

- Required commands: `npm run test:stack`, `npm run check:ci`, and `npm run build`.
- Optional/manual checks: trusted workflow dispatch after the gate reaches the default branch and GitHub Actions billing is restored.
- Regression fixtures: path parsing, numeric aliases, sibling and within-PR collisions, fork exclusion, PR/file pagination, malformed/API responses, moving heads, incomplete inventory fan-out, exact-head check publication, inventory-generation reuse, deferred lookup/create/completion races, check API failure, global publisher serialization, and trusted workflow provenance.

## Rollout

- Risk level: medium operational risk, no application-runtime risk.
- Backward compatibility: a triggering non-migration maintainer PR receives a neutral custom Check Run and successful required job; unique migration owners pass; collision and immutable-history owners fail. Fork triggers fail the required job closed and must move to a maintainer-owned branch. Scheduled refreshes skip unrelated PRs and reuse an identical completed exact-head result. Migration publishers are globally serialized without canceling the running audit, and exact heads are rechecked immediately before publication.
- Metrics/events to watch: required `Migration Collision Publisher` failures, custom `Migration Collision / Verify` audit failures, incomplete-inventory failures, and GitHub API/check-run errors.
- Follow-up slice: land migration-bearing PRs only in the SAV-241 canonical sequence, rebasing and regenerating each journal/snapshot from the actual merged predecessor.
