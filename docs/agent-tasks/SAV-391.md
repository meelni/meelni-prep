# SAV-391 Agent Task Intake

## Intent

- User request: Keep Preview in the Meelni LiveKit account without paying for
  another Ship subscription.
- Operator outcome: Staging can explicitly dispatch both the public demo and
  authenticated interview runtimes from the isolated, Meelni-owned Preview
  project on its existing Build plan.
- Why now: The Build plan accepts one hosted deployment. A second demo
  deployment failed closed at the provider's one-agent limit.

## Slice

- Primary slice: Preview LiveKit deployment topology.
- Secondary slices: Worker supervision, exact provider identity, staging
  configuration, and rehearsal evidence.
- Relevant skills: LiveKit interview runtime, codebase architecture,
  vertical-slice playbooks, Linear workstream, and engineering memory.

## Linear Tracking

- Project: Meelni.
- Parent issue: SAV-365.
- Deliverable issue: SAV-391.
- Rehearsal owner: SAV-387.

## Scope

- In scope: One Preview-only hosted deployment that starts two separately
  named worker processes; fail-together supervision; distinct health ports;
  exact source pins; staging-only provider configuration; synthetic demo and
  interview dispatch verification.
- Out of scope: Production LiveKit changes, a paid plan change, shared Statsig
  gate changes, customer data, live Stripe configuration, or deletion of the
  former personal-account Preview project.
- Assumptions: LiveKit accepts multiple registered worker processes from one
  hosted deployment when each uses a distinct dispatch name and health port.
  That assumption must be proven against the provider before staging cutover.

## Technical Plan

- Add a small Preview supervisor that starts the existing demo and interview
  entrypoints as child worker processes.
- Keep each runtime's existing metadata parser, prompt, persistence, and
  shutdown behavior unchanged.
- Give the interview worker port 8081 so it owns container health and the demo
  worker port 8082 so the SDK servers cannot collide.
- Treat either child exit as a deployment failure: terminate the sibling,
  reap both processes, and let LiveKit restart the container.
- Reject missing/duplicate dispatch names, non-Preview execution, provider
  agent-name overrides, and invalid runtime ports before starting children.
- Deploy only through a Preview-bound wrapper for the exact project and agent.

## Validation

- Unit tests for configuration, port separation, child startup, signal
  forwarding, sibling termination, and nonzero failure propagation.
- Existing Python agent/runtime contracts.
- Exact LiveKit deploy status and redacted logs showing both worker names.
- Synthetic explicit dispatch to each name, followed by a cold-start check.
- Deployment preflight and hosted staging health before rehearsal authority.

Initial provider validation on 2026-08-08 proved deployment `CA_ovn67QQ7ywmJ`
running from source `10511fb4ac919ac79db774e8b9aed4ebac13abe0`; the deployment
was then advanced with the committed provider-identity pins. Both HTTP servers
listened on their assigned ports, both dispatch names registered, and explicit
synthetic jobs reached the correct interview and demo entrypoints. The synthetic
room was deleted after verification.

## Rollout

- Update the existing Preview agent in place; do not create another agent.
- Do not update Vercel or source-owned provider pins until both workers register
  and synthetic dispatch passes.
- Roll back by redeploying the already-proven interview-only image to the same
  Preview agent. Neither rollback nor rollout touches Production.
