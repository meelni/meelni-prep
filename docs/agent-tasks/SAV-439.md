# SAV-439 Agent Task Intake

## Intent

- User request: Preserve content-free feedback-generation stage and attempt
  history with a closed provider-failure taxonomy.
- Product/user outcome: Operators can distinguish where feedback processing
  stopped or retried without storing interview content or allowing telemetry
  to delay the authoritative feedback result.
- Why now: The durable interview-to-feedback program requires replay-safe stage
  evidence before a later processing workspace can present honest lifecycle
  state.

## Slice

- Primary slice: Feedback/evaluation operations history.
- Secondary slices: database privacy, account erasure, durable workflow replay,
  and provider-neutral failure classification.
- Relevant skills: Meelni start, Linear workstream, feedback evaluation,
  codebase architecture, feedback/evaluation vertical-slice playbook,
  engineering memory, and PR preparation.

## Linear Tracking

- Project: Meelni.
- Parent slice: Interview-to-feedback reliability, Phase 1.
- Child deliverable issue: SAV-439.
- Current Linear state: In Progress.

## Scope

- In scope: One additive service-only attempt table; strict operation, stage,
  outcome, failure, timing, environment, and provider-context tuples; a
  versioned one-way generation-event fence; replay-idempotent batch writes;
  account-erasure ordering; and clean/historical migration rehearsal.
- Out of scope: Processing UI, alerts, provider configuration, live provider
  calls, Production migration, deployment, launch, or default-on activation.
- Assumptions: The feedback row and its exact raw dispatch event remain the
  authoritative workflow fence. The attempt history and existing aggregate
  event are operations evidence only.

## Product Lens

- Audience: Operators diagnosing feedback-generation reliability; no new
  customer-facing surface is included.
- Activation/retention/monetization/growth lever: Faster diagnosis of delayed
  or failed post-interview feedback supports trust and return practice.
- Product Compass note: Preserve honest feedback state without collecting a
  second copy of customer interview or provider content.

## Technical Plan

- Likely app files: None.
- Likely package/workflow files: Feedback-generation policy, operations
  normalizer, workflow buffering/flush, database store/schema/migration,
  account deletion, and migration verification fixtures.
- Data or provider dependencies: PostgreSQL/Drizzle only; sanitized,
  provider-free fixtures. No provider mutation or paid comparison.
- Docs/decisions to update: Feedback-generation and LLM-observability
  contracts plus the SAV-439 OpenSpec delta. The accepted program architecture
  remains authoritative; no new decision is required.

## Validation

- Required commands: Focused policy/normalizer/store/workflow tests, typecheck,
  test typecheck, build, calibration-runtime verification when the workflow
  bundle changes, `git diff --check`, and the full clean/historical migration
  rehearsal.
- Optional/manual checks: Review the generated SQL and snapshot for forbidden
  identity/content columns and confirm the ready PR's hosted checks reach a
  terminal result.
- Fixtures or regression tests needed: Exact replay and divergent replay,
  stale-event fencing, raw-event/session privacy, provider-context rejection,
  timestamp/duration and duration-bucket consistency, RLS/ACL, account erasure,
  synchronous recorder failure, and a non-resolving recorder.

## Rollout

- Risk level: Medium. The migration is additive, but the workflow and deletion
  paths gain a new best-effort write.
- Backward compatibility: Rolling code may omit attempt history. The ledger
  does not change feedback truth, settlement authority, deadline ownership, or
  terminal read behavior.
- Metrics/events to watch: Durable stage outcome and closed failure-class
  distributions, with the existing aggregate attempt event as fallback when a
  bounded durable flush is not accepted.
- Follow-up slice: Consume the durable content-free history in a separately
  scoped operational or customer processing projection after its authority and
  privacy boundaries are reviewed.
