# SAV-239 Agent Task Intake

## Intent

- User request: remove the self-referential stacked-PR registry gate while preserving exact, trusted topology checks.
- Product/user outcome: launch-critical stacks can advance after parent movement without default-branch SHA churn or false parent blocking.
- Why now: `expectedParentHead` made the registry update depend on the mutable value it governed.

## Slice

- Primary slice: trusted CI and engineering operations.
- Secondary slices: stack contracts and PR workflow.
- Relevant skills: Linear workstream, PR prep, engineering memory, codebase architecture.

## Linear Tracking

- Project: Meelni.
- Parent slice issue: SAV-171.
- Child deliverable issue: SAV-239.
- Current Linear state: In Progress.

## Scope

- In scope: immutable registry identity, server-side PR/ref resolution, pre-publication freshness, trigger-specific stable-context semantics, adversarial tests, and runbook/decision updates.
- Out of scope: product branches, provider configuration, database changes, and merging stacks.
- Assumptions: registry PR/ref identities are trusted default-branch configuration; PR metadata, bodies, and refs are external input; the publisher never executes PR code.

## Product Lens

- Audience: engineers, reviewers, and coding agents preparing the relaunch.
- Lever: launch reliability.
- Product Compass note: operational hotfix only; no customer-facing behavior changes.

## Technical Plan

- Likely app files: none.
- Likely workflow files: stack manifest, deterministic checker, trusted publisher/orchestrator, and tests.
- Data or provider dependencies: read-only GitHub PR metadata/ref fetches and Check Run publication; no database or product provider access.
- Docs/decisions to update: stacked-PR/tooling runbooks and a durable CI decision record.

## Validation

- Required commands: `npm run test:stack`, `npm run check:ci`, and `npm run build`.
- Optional/manual checks: trusted workflow dispatch after merge.
- Fixtures or regression tests needed: parent/child movement, stale evidence, ref refresh, wrong repository/base, missing PR/ref, closed parent, large registry fan-out, API/publication failure, and parent-versus-child stable-context outcomes.

## Rollout

- Risk level: medium operational risk, no application-runtime risk.
- Backward compatibility: existing stack identities migrate to manifest v2; evidence remains version 1; required context name remains stable.
- Metrics/events to watch: `Trusted Publisher` API/publication errors and child-bound `Stack Topology / Verify` failures.
- Follow-up slice: independent audit, merge the hotfix to `main`, then manually refresh registered stacks.
